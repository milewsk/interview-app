# Model configuration: conventions, Fluent API and annotations {mid}

EF Core builds a **model** of your entities (tables, columns, keys, indexes, relationships) from three sources, in increasing order of priority:
**conventions**, **data annotations** (attributes) and the **Fluent API** in `OnModelCreating`. Knowing the defaults matters, because they decide the
database schema and a few of them are traps.

## Important conventions

- A property named `Id` or `<Type>Id` is the **primary key**, and an integer key is generated by the database (`IDENTITY` on SQL Server).
- A non-nullable C# type gives `NOT NULL`, and a nullable one (`string?`, `int?`) gives `NULL`. With nullable reference types enabled, `string` is
  required and `string?` optional.
- `string` without a length becomes `nvarchar(max)` on SQL Server: not ideal for columns that are indexed or searched.
- `decimal` without precision becomes `decimal(18,2)`, and EF warns that values may be **silently truncated**.
- An `enum` is stored as an `int` by default.
- A collection of primitive types (`List<string>`) is stored as **JSON** in a single column (EF Core 8+), and can be queried.
- Read-only properties without a setter (computed from others) aren't mapped.

## Fluent API and `IEntityTypeConfiguration<T>`

```csharp
public class ProductConfiguration : IEntityTypeConfiguration<Product>
{
    public void Configure(EntityTypeBuilder<Product> b)
    {
        b.ToTable("Products");
        b.Property(p => p.Name).HasMaxLength(200).IsRequired();      // nvarchar(200) NOT NULL
        b.HasIndex(p => p.Sku).IsUnique();                             // CREATE UNIQUE INDEX
        b.HasIndex(p => p.Name).HasFilter("[IsDeleted] = 0");          // filtered index
        b.Property(p => p.Price).HasPrecision(10, 2);                  // decimal(10,2)
        b.Property(p => p.Status).HasConversion<string>().HasMaxLength(20);   // enum as text
        b.Property<DateTime>("CreatedAt").HasDefaultValueSql("CURRENT_TIMESTAMP");   // shadow property
        b.Ignore(p => p.DisplayName);
    }
}

protected override void OnModelCreating(ModelBuilder modelBuilder)
{
    modelBuilder.ApplyConfigurationsFromAssembly(typeof(AppDbContext).Assembly);
    modelBuilder.Entity<OrderLine>().HasKey(l => new { l.OrderId, l.ProductId });   // composite key
}
```

Keeping configuration in separate `IEntityTypeConfiguration<T>` classes keeps `OnModelCreating` short and the domain classes free of persistence
details. `ApplyConfigurationsFromAssembly` picks them all up.

## Annotations or Fluent API?

Annotations (`[Key]`, `[Required]`, `[MaxLength(200)]`, `[Column(TypeName = "...")]`, `[Index(nameof(Sku), IsUnique = true)]`, `[Precision(10, 2)]`)
are short and visible on the class, and `[Required]`/`[MaxLength]` are also used by ASP.NET Core validation. The Fluent API can do **everything** (e.g.
composite keys, filtered indexes, converters, relationships, table splitting, query filters) and keeps entities free of EF attributes. Many teams use
the Fluent API exclusively for consistency. When both are used, the Fluent API wins.

## Model-wide conventions

```csharp
protected override void ConfigureConventions(ModelConfigurationBuilder builder)
{
    builder.Properties<string>().HaveMaxLength(256);        // default length for all strings
    builder.Properties<decimal>().HavePrecision(18, 4);
    builder.Properties<Money>().HaveConversion<MoneyConverter>();
}
```

## Value converters

A converter maps a CLR type to a database type: enums as text (`HasConversion<string>()`), strongly typed IDs (`OrderId` → `int`), encryption, a value
object to a single column. The downside: a query can compare only the converted value, and some operations (e.g. `Contains` on part of the text) can't be
translated.

## Keys and value generation

- **Surrogate keys**: `int`/`long` with `IDENTITY` (or a sequence, or HiLo), or `Guid`. Random `Guid.NewGuid()` values fragment a clustered index, so EF
  generates **sequential GUIDs** for SQL Server by default, and .NET 9+ has `Guid.CreateVersion7()` (time-ordered).
- **Natural keys** (e.g. a SKU) as the primary key are rarely a good idea, because they can change. Use a unique index instead.
- `ValueGeneratedOnAdd`, `HasDefaultValue`/`HasDefaultValueSql`, `HasComputedColumnSql` configure values generated by the database.

## Questions

### How does EF Core recognize the primary key without configuration? {junior}

By convention a property named `Id` or `<TypeName>Id` (e.g. `ProductId`) becomes the primary key. If it's an integer or a `Guid`, EF assumes the value is
generated when inserted: for `int` the database uses `IDENTITY` (SQL Server) or autoincrement, and for `Guid` EF generates it on the client. A different
key or a composite key is configured with `HasKey` or `[Key]`/`[PrimaryKey]`.

### Fluent API or data annotations? {junior}

Annotations are simpler and visible on the class, but can express only part of the configuration. The Fluent API can configure everything (composite
keys, filtered indexes, converters, relationships, query filters) and keeps domain classes free of EF-specific attributes. Fluent API configuration takes
precedence over annotations. A common choice is the Fluent API in `IEntityTypeConfiguration<T>` classes, loaded with `ApplyConfigurationsFromAssembly`.

### What column type does a `string` without configuration get on SQL Server, and why does it matter? {mid}

`nvarchar(max)` (or `NOT NULL` depending on nullability). Such columns can't be used as keys of a regular index and are stored and processed less
efficiently, so they're bad for anything searched or indexed. You set a length with `HasMaxLength` or `[MaxLength]`, or globally in `ConfigureConventions`
(`Properties<string>().HaveMaxLength(256)`).

### Why does EF warn about `decimal` properties without precision? {mid}

Without configuration, a `decimal` maps to `decimal(18,2)` on SQL Server, and values with more decimal places or larger magnitude are silently truncated or
rounded, which is dangerous for money, rates or quantities. EF logs a warning during model building. Configure the precision explicitly: `HasPrecision(19, 4)`,
`[Precision(19, 4)]` or a global convention.

### How is an `enum` stored, and how do you change it? {mid}

By default as an `int` with the enum's numeric value. That's compact, but the data is unreadable in the database, and reordering enum members breaks existing
data. `HasConversion<string>()` stores the name as text (preferably with `HasMaxLength`), which is readable and resilient to reordering but breaks on
renaming. Global configuration is possible in `ConfigureConventions`.

### What is a value converter, and what are its limitations? {mid}

A mapping between a property's CLR type and the type stored in the database, e.g. an enum as a string, a strongly typed `OrderId` as `int`, a value object
as a single column, or encrypted text. It's configured with `HasConversion`. Limitations: the database only knows the converted value, so operations on the
original type (e.g. a method called on the value object, partial comparisons) can't always be translated to SQL, and converters aren't applied to raw SQL.

### How do you configure a unique or filtered index? {junior}

With the Fluent API: `HasIndex(p => p.Sku).IsUnique()` creates a unique index, and `.HasFilter("[IsDeleted] = 0")` a filtered index covering only some rows
(e.g. uniqueness among non-deleted records). The annotation `[Index(nameof(Sku), IsUnique = true)]` on the class is an alternative. A unique index is also the
right way to enforce uniqueness of natural keys, such as an email or SKU, while keeping a surrogate primary key.

### Why can random `Guid` keys hurt performance, and what can you do? {senior}

Random GUIDs inserted into a clustered index land in random positions, which causes page splits, fragmentation and poor cache usage. EF Core generates
sequential GUIDs for SQL Server keys by default, which avoids the problem if you let EF generate the value. When the application creates keys itself, use a
time-ordered format such as `Guid.CreateVersion7()` (.NET 9+), or keep a non-clustered GUID key and a clustered integer column.

### What are shadow properties? {mid}

Properties that exist in the EF model and in the database, but not in the entity class, e.g. foreign keys without a CLR property, or audit columns like
`CreatedAt`. They're configured with `Property<DateTime>("CreatedAt")`, read and set through `Entry(entity).Property("CreatedAt")`, and used in queries with
`EF.Property<DateTime>(e, "CreatedAt")`. They keep infrastructure details out of the domain model.

### What does `ConfigureConventions` give you? {mid}

It lets you configure all properties of a given type at once, before the model is built: e.g. a default length for all strings, precision for all decimals,
or a converter for all properties of a value object type (`Properties<Money>().HaveConversion<MoneyConverter>()`). This removes repetitive per-property
configuration and makes consistency the default. Individual properties can still override these settings.
